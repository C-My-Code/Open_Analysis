# ADR-0005: gmsh is the only mesher; Triangle is prohibited

- Status: Accepted (2026-10-27)

## Context
- We need meshes for 2D cross-sections (BEM does not, FEM does), 2D copper sheets (DC IR, AC PDN cavities) and 3D volumes (Palace, Elmer, and later thermal/quasi-static FEM).
- Triangle (Shewchuk) is fast but is not OSI-licensed: it forbids commercial use without permission. KiPI depends on it.
- gmsh is GPL-2+ with a linking exception, has a pip wheel and a Python API, an OCC kernel for 3D booleans, and size fields.

## Decision
- **gmsh** (pip wheel, pinned minor version) is the single mesher, wrapped by `oa_mesh`:
  - `mesh_cross_section` and `mesh_copper_sheets` (WP-109);
  - `build_occ_model` and `write_msh` (WP-206).
- gmsh runs **in-process but only inside worker processes**, one model per process at a time, through `oa_mesh._session`. The server and CLI processes never initialize it.
- Meshes are deterministic: a fixed `General.RandomSeed`, `Mesh.Algorithm=6` (2D) and `Mesh.Algorithm3D=10`. The gmsh version is part of task cache keys.
- openEMS uses its own rectilinear grid generated by the adapter, not gmsh.
- **Triangle, meshpy and other Triangle wrappers are prohibited.** The license audit blocks them. Netgen and MMG (LGPL) are allowed fallbacks only through a new ADR.
- The DC IR raster FVM reference solver and the thermal layered FVM use structured grids and need no mesher.

## Consequences
- gmsh's global state forces worker-process isolation, which the job system provides anyway.
- Polygon healing (slivers, fractured KiCad fills) is our responsibility. It is done in shapely before meshing, with tolerances in `oa_mesh` config.
